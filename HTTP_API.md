# ESP32: HTTP API v1 и структура прошивки

ESP32 обслуживает HTTP на порту 80. Путь API — `/api/v1`. Приложение и скрипты используют
короткие независимые запросы: контекст `with EspAdc(...)` не занимает соединение до выхода.
Для перехода нужно загрузить новую прошивку ESP-IDF и перезапустить обновлённое приложение.
Сохранённые адрес и порт используются дальше; адаптер автоматически переключается на HTTP.
Arduino в этой реализации не используется.

## Методы

| Метод | Путь | Назначение / тело JSON |
| --- | --- | --- |
| GET | `/api/v1/status` | Состояние устройства, API, Wi-Fi, АЦП, RTC, SD и записи |
| GET | `/api/v1/config` | Действующие настройки опроса, обработки и записи |
| PUT | `/api/v1/config` | Полная конфигурация из 8 полей; применить и сохранить в NVS |
| GET | `/api/v1/ip` | IP устройства |
| GET | `/api/v1/adc` | Последняя точка: метка UTC, номер и три канала в мВ |
| GET | `/api/v1/adc/gain` | Текущий индекс диапазона |
| PUT | `/api/v1/adc/gain` | `{"gain":1}`, целое 0–5 |
| GET | `/api/v1/rtc` | Текущее время RTC |
| PUT | `/api/v1/rtc` | `{"utc":"2026-10-12T15:30:45"}`; UTC, 2000–2099 |
| GET | `/api/v1/wifi` | Режим, SSID, IP/MAC обоих интерфейсов; пароль не возвращается |
| PUT | `/api/v1/wifi` | `{"mode":"own","ssid":"esp","password":"12345678"}` |
| GET | `/api/v1/recording` | Состояние записи, имя и последняя ошибка |
| POST | `/api/v1/recording/start` | `{"filename":""}` для автоимени, либо имя файла |
| POST | `/api/v1/recording/stop` | Остановить запись и сбросить буфер; `{}` |
| GET | `/api/v1/files` | `{"files":[{"name":"...","size":123}]}` |
| GET | `/api/v1/files/имя.txt` | Скачать файл |
| DELETE | `/api/v1/files/имя.txt` | Удалить файл |
| POST | `/api/v1/sd/mount` | Инициализировать SD; `{}` |
| POST | `/api/v1/sd/unmount` | Отключить SD для извлечения; `{}` |

Изменения состояния выполняются через PUT/POST/DELETE. GET ничего не меняет, кроме
служебного сброса буфера при скачивании текущей записи для получения согласованного снимка.
Поддерживаются OPTIONS и CORS для браузерных клиентов. Максимальное тело JSON — 1024 байта.
`GET /` возвращает тот же статус, что `/api/v1/status`.

Пример измерения:

```json
{"timestamp_ms":1791819045123,"sequence":123,"adc0_mv":100,"adc1_mv":200,"adc2_mv":300}
```

`timestamp_ms` — Unix-время UTC в миллисекундах. Все клиенты читают последний снимок
одного общего процесса измерений; HTTP-запрос не запускает ещё одно преобразование АЦП.
`sequence` увеличивается при каждой завершённой усреднённой точке и позволяет распознавать повторный снимок.
Опрос быстрее частоты сбора может возвращать ту же точку. Настройки и запись общие для
устройства; одновременные клиенты не получают отдельные записи на SD.

## Настройки измерений и сохранение

В интерфейсе: **Настройки → Сбор и запись → Прочитать с ESP**. После изменения нажмите
**Применить и сохранить**. Изменения действуют без перезагрузки и сохраняются во внутренней
флеш-памяти ESP32 (NVS, namespace `acquisition`, один версионированный blob `config`).
Чтение настроек и обычные измерения NVS не перезаписывают; повторное сохранение уже сохранённой
конфигурации тоже не пишет флеш. Wi-Fi хранится отдельно в `wifi-settings`.
Время продолжает храниться в DS1302 с батарейкой, а не в конфигурации NVS.

| Поле | Значение по умолчанию | Допустимо | Смысл |
| --- | --- | --- | --- |
| `sample_interval_ms` | 10 | 10–60000, шаг 10 мс | Интервал опроса всех трёх каналов АЦП |
| `average_samples` | 1 | 1–1000 | Размер неперекрывающегося окна арифметического среднего |
| `ema_alpha` | 0.25 | 0.01–1 | EMA после усреднения: меньше — сильнее сглаживание, 1 отключает |
| `record_every` | 1 | 1–10000 | Записать первую усреднённую точку, затем каждую N-ю |
| `flush_samples` | 860 | 1–860 | Сбросить буфер на SD при накоплении N точек |
| `flush_interval_ms` | 1000 | 100–60000, шаг 10 мс | Ожидание сброса с момента первой точки в буфере |
| `rtc_poll_interval_ms` | 20 | 20–200, шаг 10 мс | Чтение секунд DS1302; это отдельная задача |
| `gain` | 1 | 0–5 | Индекс диапазона ADS1115, как в `/adc/gain` |

`PUT /api/v1/config` заменяет весь набор: сначала прочитайте GET, измените нужные поля и отправьте
все восемь. Неизвестные, отсутствующие и некорректные поля отклоняются с 400. Изменение во время
записи, при несохранённом буфере либо перед перезапуском Wi-Fi отклоняется с 409.
При ошибке сохранения в NVS возвращается 500, прежняя рабочая конфигурация сохраняется.
Совместимый `PUT /adc/gain` также сохраняет диапазон в этой конфигурации, в том числе при
отсутствующем АЦП — диапазон применится, когда датчик станет доступен.

```json
{"sample_interval_ms":10,"average_samples":10,"ema_alpha":1,"record_every":1,"flush_samples":100,"flush_interval_ms":1000,"rtc_poll_interval_ms":20,"gain":1}
```

В этом примере три канала опрашиваются примерно 100 раз/с, по десяти измерениям получается
одна точка — примерно 10 точек/с. Все усреднённые точки записываются, буфер сбрасывается
примерно раз в секунду либо при накоплении 100 точек, что наступит раньше.
Частоты целевые: медленное оборудование/SD может удлинить интервал; пропущенные опросы
не догоняются серией мгновенных измерений. `sample_hz` и `output_hz` в статусе — расчётные частоты.

Метка точки берётся по последнему измерению окна. Неполное окно ещё не является точкой;
при начале записи, смене настроек/времени или потере АЦП/RTC окно и EMA сбрасываются.
Мониторинг отдаёт каждую завершённую усреднённую точку; `record_every` влияет только на SD.
В интерфейсе повторные чтения той же точки не добавляют дубликаты на график.
Остановка и скачивание текущего файла сразу сбрасывают готовые накопленные точки.
Таймер сброса основан на монотонном таймере ESP, независимо от показаний RTC и периода АЦП.
До сброса данные находятся в RAM и могут потеряться при отключении питания.

Увеличение интервала RTC снижает частоту чтения часов, но увеличивает неопределённость момента
смены секунды приблизительно до этого интервала. Миллисекунды интерполируются таймером ESP;
точность 1 мс сам DS1302 не обеспечивает.

```python
with EspAdc(host="192.168.0.163", port=80) as device:
    config = device.get_config()
    config.update(average_samples=10, ema_alpha=1, flush_interval_ms=1000)
    device.set_config(config)
```

Скачивание передаётся с HTTP chunked encoding. `X-File-Size` содержит размер снимка в байтах;
даже если запись продолжается, в ответ не попадают дописанные после начала скачивания строки.
Приложение проверяет размер, пишет в `.part` и заменяет целевой файл только после полного
скачивания. Отмена выполняется без принудительного уничтожения потока.

## Ошибки и конфликты

| HTTP | Причина |
| --- | --- |
| 400 | Некорректные JSON, дата, диапазон или имя файла |
| 404 | Неизвестный endpoint или отсутствующий файл |
| 405 | Неподходящий HTTP-метод |
| 408 | Не получено тело запроса за отведённое время |
| 409 | Конфликт с текущей записью, скачиванием, именем или перезапуском |
| 413 | Слишком большое тело запроса |
| 500 | Ошибка оборудования / файловой системы |
| 503 | АЦП/RTC/SD недоступны либо очередь HTTP заполнена |

```json
{"error":{"code":"conflict","message":"Recording already active"}}
```

Существующий файл не перезаписывается. Допустимы имена до 32 символов из букв ASCII, цифр,
`_`, `-`, `.`; имя не начинается с точки и не содержит путь. Автоимя:
`data_YYYYMMDD_HHMMSS_mmm.txt` по UTC.

Во время записи запрещены изменение RTC, диапазона АЦП, Wi-Fi, отключение SD и удаление
текущего файла. После остановки нужно успешно сбросить буфер, затем можно извлекать SD.
Во время скачивания нельзя удалить скачиваемый файл или отключить карту. Одновременно
разрешены два скачивания; оставшиеся HTTP workers могут обслуживать мониторинг.

При потере RTC/АЦП запись останавливается с сохранением валидного буфера. При ошибке записи
прошивка пытается вернуть файл к размеру до неудачного пакета и сохраняет буфер для повторного
`stop`. Если откат не удался, повторная запись пакета блокируется, чтобы не дублировать строки;
сообщение требует проверки файла перед перезапуском устройства. Буфер в RAM не переживает
отключение питания. SD не форматируется автоматически.

Изменение Wi-Fi сохраняется в NVS и запускает перезагрузку через секунду, чтобы успеть
вернуть HTTP-ответ. Пока перезапуск ожидается, новая запись не запускается.

## Примеры

Адрес в режиме собственной точки доступа обычно `192.168.4.1`; при подключении к роутеру
используйте полученный адрес ESP32. Новое устройство без сохранённых настроек создаёт
точку доступа `esp` с паролем `12345678`; существующие настройки NVS сохраняются.

Заводские MAC подключённой ESP32 прочитаны и зафиксированы в `board_config.h`:

| Интерфейс | MAC |
| --- | --- |
| STA: подключение к роутеру | `68:09:47:9f:21:2c` |
| AP: собственная сеть ESP | `68:09:47:9f:21:2d` |

Адреса не меняются местами. STA прочитан из eFuse через esptool; AP подтверждается
`esp_read_mac(ESP_MAC_WIFI_SOFTAP)` и логами запуска ESP-IDF. Ранее заданный
`7c:b0:c2:f1:06:8f` оказался MAC клиента, подключённого к точке доступа ESP32.

Допустимые режимы Wi-Fi:

- `own`: собственная сеть с указанными SSID/паролем.
- `other`: подключение к роутеру с указанными SSID/паролем; при неудаче резервная сеть `esp`.
- `both`: одновременные AP+STA. SSID/пароль в запросе относятся к роутеру; ESP также создаёт
  сеть `esp` с паролем `12345678`. Она доступна и при отсутствии соединения с роутером.

В приложении режим `both` называется **«Сеть ESP + роутер»**. HTTP API доступен по адресу
роутера и по адресу собственной сети, обычно `192.168.4.1`. `GET /api/v1/wifi` дополнительно
возвращает объекты `station` и `access_point` с адресами, MAC и признаками доступности;
основное поле `ip` предпочитает адрес роутера, иначе адрес AP.

Для одновременной работы MAC должны быть разными
([ограничение ESP-IDF](https://docs.espressif.com/projects/esp-idf/en/v5.0.3/esp32/api-reference/network/esp_wifi.html#_CPPv416esp_wifi_set_mac16wifi_interface_tPK7uint8_t)).
Оба интерфейса используют один радиоканал, выбранный подключением к роутеру
([режим AP+STA](https://docs.espressif.com/projects/esp-idf/en/latest/esp32/api-guides/wifi-driver/overview.html)).
Маршрутизация интернета между сетями не включена. Подсети AP и роутера должны различаться.

Пример включения AP+STA:

```json
{"mode":"both","ssid":"имя роутера","password":"пароль роутера"}
```

### Настройка роутера перед прошивкой

Скопируйте `esp_adc/main/wifi_config.example.h` в `esp_adc/main/wifi_config.local.h`
и заполните `SSID`, `PASSWORD`, `REVISION`. Локальный файл исключён из Git.
При первой загрузке с новой `REVISION` прошивка сохраняет эти параметры в NVS
и включает `both`: подключение к роутеру плюс собственная сеть `esp` / `12345678`.
При последующих загрузках с той же ревизией используются сохранённые настройки,
включая изменения через приложение. Для повторного применения файла измените `REVISION`
и перепрошейте плату. Без локального файла используются NVS либо стандартная сеть ESP.


```sh
curl http://192.168.4.1/api/v1/status
curl http://192.168.4.1/api/v1/adc
curl -X PUT http://192.168.4.1/api/v1/rtc -H 'Content-Type: application/json' \
  -d '{"utc":"2026-10-12T15:30:45"}'
curl -X POST http://192.168.4.1/api/v1/recording/start -H 'Content-Type: application/json' -d '{}'
curl -X POST http://192.168.4.1/api/v1/recording/stop -H 'Content-Type: application/json' -d '{}'
```

Python-клиент использует только стандартную библиотеку для HTTP:

```python
from api import EspAdc

with EspAdc(host="192.168.4.1", port=80) as device:
    print(device.get_status())
    timestamp_ms, channels = device.read_sample()
    print(timestamp_ms, channels)
    print(device.get_rtc_time())
```

Отдельный монитор: `python simple_monitor.py --host 192.168.4.1 --rps 5`.
Вспомогательные команды запускаются как модули: `python -m simple_commands.start_record`,
`python -m simple_commands.stop_record`, `python -m simple_commands.chech_status`.
Ошибки API в Python представлены `DeviceApiError` с полями `status` и `code`.

## Структура

```text
esp_adc/main/
  main.cpp                     создание компонентов и запуск
  board_config.h               пины, частоты, буферы и пределы параллелизма
  domain/models.h              точки, состояния, ошибки и правила имён файлов
  domain/ports.h               контракты АЦП, часов, SD и сети
  application/daq_service.*    сбор, снимки, запись и правила совместимости операций
  hardware/adc.*               ADS1115, I2C, диапазон, EMA и восстановление
  hardware/clock.*             GPIO/FreeRTOS-адаптер часов
  ds1302.h                     драйвер и календарь DS1302
  hardware/storage.*           SPI/FAT, файловые операции и время жизни чтения
  hardware/network.*           Wi-Fi, IP, NVS и отложенная перезагрузка
  platform/mutex.h             RAII для FreeRTOS mutex
  transport/http_protocol.h    пути, версии и допустимые методы
  transport/http_api.*         HTTP, JSON, worker queue и потоковое скачивание
```

Сервис получает аппаратные зависимости через интерфейсы `domain/ports.h`. Транспорт
обращается к сервису и не управляет GPIO или глобальными буферами. В Python `api/routes.py`
задаёт endpoint-ы, `HttpAdapter` отвечает за HTTP и файлы, `EspAdc` — за методы устройства,
а Qt widgets — за отображение и действия пользователя.

Мьютексы и порядок блокировок:

- **Состояние сервиса**: переходы записи, буфер и конфликтующие изменения. Вложенные
  блокировки идут только из сервиса к адаптерам.
- **Последний снимок**: короткое копирование точки; этот mutex не удерживается при I/O.
- **АЦП**: весь набор из трёх преобразований и смена диапазона. Выборка не смешивает диапазоны.
- **RTC**: чтение GPIO, установка и опорная метка таймера.
- **SD**: операции файловой системы и список активных читателей. Блокировка снимается перед
  отправкой данных в сеть. Reader закрепляет файл и карту до закрытия и читает фиксированный размер.
- **Сеть**: запись настроек NVS и защита от повторного перезапуска.

Смена времени/диапазона и начало записи меняют поколение состояния: точка, начавшая
преобразование до изменения, не попадает в новую запись. Четыре HTTP workers получают
асинхронные запросы; медленный приём тела или отправка файла не удерживают задачу сервера.
Используется [асинхронный HTTP server ESP-IDF](https://docs.espressif.com/projects/esp-idf/en/v5.5/esp32/api-reference/protocols/esp_http_server.html).

Буфер скачивания 4096 байт выделяется в куче только на время передачи, с проверкой ошибки
выделения. Он не занимает стек обычных HTTP-запросов. Лимит двух скачиваний ограничивает
эти буферы 8 КиБ. Размер стека worker — 6144 байта; минимальный оставшийся запас виден
в USB-логе `Worker stack minimum free`. Сборка запрещает кадры функций больше 2048 байт.

На показанной плате ESP32-WROOM-32U внешняя PSRAM не предусмотрена; 4 МБ flash — хранилище
прошивки, а не дополнительная оперативная память
([спецификация модуля](https://documentation.espressif.com/esp32-wroom-32d_esp32-wroom-32u_datasheet_en.html)).
Поэтому `CONFIG_SPIRAM` для этой платы не включён. На модуле с PSRAM часть сетевых выделений
можно направить туда через `CONFIG_SPIRAM_TRY_ALLOCATE_WIFI_LWIP`; это не перенос всех задач
и стеков Wi-Fi во внешнюю память.

## Проверки

Аппаратный тест `tests/idf_http_smoke.cpp` включается только явно:
`idf.py -DDAQ_HTTP_SMOKE_TEST=ON build flash`. Он запускает на ESP32 три параллельных клиента,
которые выполняют 600 запросов к настоящему HTTP-серверу через lwIP, проверяя коды,
длину и JSON ответов. Настройки и файлы тест не меняет. Результат — в USB-логе `http_test`.
После проверки обязательно собрать и прошить `idf.py -DDAQ_HTTP_SMOKE_TEST=OFF build flash`,
чтобы тест не запускался при каждом включении. Этот тест не проверяет радиосвязь с внешним клиентом.

Дополнительный `-DDAQ_CONFIG_SMOKE_TEST=ON` вместе с HTTP-тестом включает проверку записи
всех восьми параметров через HTTP, отклонения некорректной конфигурации и восстановления
из NVS после автоматической перезагрузки. Исходные значения затем восстанавливаются.
Эта проверка пишет конфигурацию и выполняется один раз на NVS (маркер в `cfg-selftest`).
В рабочей сборке оба флага должны быть `OFF`.

Проверка конфигурации выполнена на подключённой ESP32: USB-лог подтвердил
`PASS: all 8 fields survived reboot; original config restored`, затем `600 passed, 0 failed`.
В тестах сервиса проверены арифметическое среднее, EMA, отбор точек для записи, сброс по
количеству и монотонному времени, восстановление конфигурации и ошибка сохранения NVS.
Новая форма настроек проверена на 800×600 без прокрутки. Реальное усреднение входного сигнала
и запись на карту требуют подключённых ADS1115 и SD.
После финальной прошивки без тестов параметры восстановились, AP `esp` и HTTP запустились.
В последнем наблюдении STA повторял попытки подключения к роутеру (причины 2/205),
получение адреса при этой загрузке не подтверждено; ранее роутер выдавал `192.168.0.163`.

Сборка: ESP-IDF 5.5.1, ESP32. Проверены драйвер RTC, сервис с конкурентными вызовами и
ошибками, HTTP-клиент на локальном сервере (включая четыре клиента при скачивании), UTC,
частичные загрузки и интерфейс на 800×600. На физической ESP32 после исправления стека
повторный тест завершился `600 passed, 0 failed`, без перезагрузок и предупреждений
`httpd_sock_err`. Минимальный запас стека HTTP — 3060 байт, внутренней кучи — 115024 байта
(включая три дополнительных тестовых клиента). Это измерения проверенных маршрутов;
передачу реального файла без подключённой SD проверить нельзя.

Через USB подтверждены оба заводских MAC, одновременный AP `esp` и подключение к `ASC_WiFi`
с выданным адресом `192.168.0.163` (DHCP может его изменить). Прямой HTTP-запрос с этого Mac
пока не прошёл, хотя MAC контроллера виден в ARP; внешняя доступность API требует отдельной
проверки. АЦП ADS1115 и SD на текущей плате недоступны, поэтому запись и скачивание с реальной
карты не проверены. Рабочая прошивка загружается с выключенным аппаратным автотестом.
